  <action>
    Create `run.sh` at the repository root and make it executable (`chmod +x run.sh`). This is the
    first `.sh` file in the repository; `.gitattributes` with the shell line-ending rule was
    committed in plan 01-01 specifically so this file checks out with LF endings on every clone.

    Line 1 is `#!/usr/bin/env bash`. Line 2 is `set -euo pipefail` (RUN-03: fail fast and propagate
    non-zero). Because `set -u` is active, every parameter expansion of a possibly-unset variable
    must use the `${VAR:-}` form — including `${OSTYPE:-}` and `${1:-}`.

    Immediately after strict mode, add the platform guard for ENV-06: a `case "${OSTYPE:-}" in`
    matching `msys*` and `cygwin*` that exports `MSYS_NO_PATHCONV=1`, with no action for any other
    value. MSYS2 rewrites POSIX-looking arguments into Windows paths before invoking `docker.exe`,
    which corrupts container-side paths. Guarding on OSTYPE makes the export a no-op on Linux and
    macOS. Pair this with a discipline the rest of the script follows: every argument handed to a
    container is a path relative to the compose-declared `working_dir`, never an absolute
    container path. The two mitigations are independent — the guard handles the case where an
    absolute path is unavoidable, and the relative-path discipline means that case does not arise
    in Phase 1.

    Define a helper `env_value NAME` that reads a value out of `.env` without executing the file:
    select the last line matching `^NAME=`, strip the key and the `=`, and print the remainder. Do
    NOT source or dot-include `.env` — a config file should not be able to run arbitrary shell, and
    parsing avoids surprises with values containing spaces or quotes.

    Define a helper `require_file PATH MESSAGE` that exits 1 with MESSAGE on stderr when PATH does
    not exist. This is what makes `job` and `test` fail before touching docker.

    Define `run_step LABEL COMMAND...` implementing the output style in D-12: lean steps with full
    detail on failure, and no verbose flag. It captures combined stdout and stderr of the command
    into a temp file, prints one line for the step with a status marker on success, and on failure
    prints the step line with a failure marker followed by the entire captured output on stderr,
    then returns the command's exit status. The invocation must be written so `set -e` does not
    abort before the failure branch runs — put the command inside an `if ... then ... else` and
    capture `$?` in the else branch. Always remove the temp file. The status markers and exact log
    formatting are yours to choose (this is an explicit Claude's-discretion item in 01-CONTEXT.md);
    keep them ASCII so Git Bash renders them.

    Define `preflight` running these checks in order, each with an actionable remedy on failure
    (D-13):
      1. `docker info` succeeds. Remedy: start Docker Desktop (or the docker daemon) and retry.
      2. `docker compose version` succeeds. Remedy: install the Docker Compose v2 plugin.
      3. `docker compose up --help` output mentions the wait flag — a capability probe rather than
         version-string parsing. Remedy: upgrade to Docker Compose v2.1.1 or newer.
      4. `.env` exists. Remedy: print the literal command `cp .env.example .env`. The script MUST
         NOT create the file itself — the adopter should learn that the file exists, because that is
         where they will make their changes.
      5. Each of PROJECT_NAME, AWS_ENDPOINT_URL, AWS_DEFAULT_REGION, AWS_ACCESS_KEY_ID,
         AWS_SECRET_ACCESS_KEY resolves through `env_value` to a non-empty value. On failure, name
         the specific variable in the message and point at `.env.example`. This is the resolution of
         the ENV-04 empty edge: a present-but-blank variable is a distinct failure from a missing
         `.env`, and it must not be allowed to reach a container as an empty string.
      6. AWS_ENDPOINT_URL does not contain `amazonaws.com`. On failure, state that run.sh drives the
         local emulator only and refuse to continue. This is the mitigation for T-01-03: without it,
         a mistyped endpoint sends dummy-credentialed calls at a real AWS account.

    Define `usage` printing a fixed block listing all eight subcommands in this exact order, each on
    one line with a short description: `up`, `down`, `bootstrap`, `seed`, `job`, `test`, `lint`,
    `demo` (RUN-01, RUN-02, D-11 — eight, which supersedes RUN-02's original list of six). Write it
    as a literal printf or heredoc block, not a loop over an associative array, so the order is
    fixed and the output is byte-stable across invocations.

    Define the dispatcher at the bottom of the file: an exact-match `case "${1:-}"` over the eight
    literal subcommand names, each branch calling the corresponding `cmd_<name>` function; `-h` and
    `--help` printing usage to stdout and exiting 0; the empty string printing usage to stderr and
    exiting 2; and a default branch printing an unknown-subcommand message plus usage to stderr and
    exiting 2. Before dispatching, reject extra arguments: no subcommand in this phase takes any, so
    a second positional argument is a usage error exiting 2. There is no prefix matching — `u` is
    not `up`. Route argv only through this case statement; never build a command string from user
    input and hand it to a shell (T-01-04).

  <action>
    Add the eight `cmd_*` functions to `run.sh`, above the dispatcher. Every one of them calls
    `preflight` first, either directly or by delegating to a function that does. Every container
    invocation uses the explicit `--profile` form so behaviour does not depend on which Compose
    minor version auto-enables a service's profile.

    `cmd_up` (D-09) — one `run_step` bringing up the emulator with
    `docker compose up -d --wait floci`, which blocks on the image's own health probe instead of
    polling an HTTP endpoint from the host; then calls `cmd_bootstrap`; then calls `cmd_seed`; then
    prints a short closing summary naming what now exists. The compose-up step comes first, then
    bootstrap, then seed, in that fixed order. Because strict mode is on and `run_step` returns the
    command's status, a failure at any step aborts the chain immediately and propagates that step's
    exit code — the bootstrap failure must never be followed by a seed attempt. `up` leaving a
    catalog that points at empty paths is not a useful state, which is why the metadata and data
    steps are chained here even though they remain separately callable.

    `cmd_down` — `docker compose down -v --remove-orphans`, wrapped in one `run_step`. The volume
    removal is what makes "down leaves nothing running" true for a `memory`-mode emulator plus any
    anonymous volumes a `run --rm` left behind.

    `cmd_bootstrap` (D-05) — one `run_step` running
    `docker compose --profile tools run --rm tools python catalog/bootstrap.py`. The script path is
    relative to the compose-declared `working_dir`, which is what keeps MSYS from rewriting it.

    `cmd_seed` — one `run_step` running
    `docker compose --profile tools run --rm tools python catalog/seed.py`.

    `cmd_job` (D-07) — call `require_file jobs/csv_to_parquet/job.py` FIRST, before printing anything
    and before touching docker, so that on a Phase 1 clone this subcommand fails immediately and no
    ~4.77 GB image fetch is triggered. Only after that guard passes, print the warning that the first
    run downloads roughly 4.8 GB of Glue image, then `run_step` the invocation
    `docker compose --profile glue run --rm glue spark-submit jobs/csv_to_parquet/job.py --JOB_NAME
    csv_to_parquet`. There is deliberately no separate pull or warm subcommand; the warning on first
    `job` is the whole mechanism.

    `cmd_test` — call `require_file tests` first (same reasoning as `cmd_job`: fail before the image
    fetch). Then `run_step` the invocation `docker compose --profile glue run --rm glue -c "python3
    -m pytest --disable-warnings"`. The `-c "<shell command>"` form is required by this image's
    entrypoint; a bare command is not executed.

    `cmd_lint` — two `run_step` calls against the tools service:
    `docker compose --profile tools run --rm tools ruff check .` and then
    `docker compose --profile tools run --rm tools ruff format --check .`. This must exit 0 on a
    clean clone, which it does trivially while no Python file exists and must continue to do once
    plan 01-03 adds them.

    `cmd_demo` (D-10) — call `cmd_up`, then `cmd_job`, then `cmd_test`, then print a summary report
    naming what ran. This is the single command the README will lead with in Phase 4 and the one
    that satisfies RUN-04 in Phase 2. On a Phase 1 clone it reaches `cmd_job` and stops there with a
    non-zero exit, which is the correct behaviour: the job script does not exist yet and RUN-04
    belongs to Phase 2.
  </action>

## Flagged assumptions carried by this plan

1. **`MSYS_NO_PATHCONV` effectiveness across Git Bash versions is unverified** and unverifiable on
   Linux CI (REQUIREMENTS.md Open Design Questions; PITFALLS Pitfall 11). Recorded as a backstop
   truth. The manual Windows verification checkpoint in plan 01-03 is the only evidence this project
   will have.
2. **`docker compose up --wait` availability.** Preflight probes for the flag rather than parsing a
   version string, so an old Compose fails with a named message instead of an obscure one. If an
   adopter's Compose lacks it, they must upgrade; no polling fallback is authored, because two
   readiness mechanisms would be two things to keep correct.
3. **Concurrency behaviour under two simultaneous `up` invocations** is a backstop, not a truth.
